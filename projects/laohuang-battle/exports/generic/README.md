# generic Export · laohuang-battle

This is a **generic engine** handoff package, for targets without a specialized exporter yet.
`native_project_files: false` — provides deterministic JSON only; native project files of any engine are outside the built-in scope.

> Agent goal: read the JSON in this directory and **map and apply** the generated UI to the target engine/framework (custom rendering, Flutter, Unity UI Toolkit, in-house editors, etc.).

## Contents

| File | Purpose |

## Agent Quickstart (Read Me → Run It)

Goal: after this section, the Agent can drop the demo into a generic target project and get a clickable 7-screen skeleton without asking questions or editing generated files.
Real business logic is out of scope here (all demo events only log `[kui-demo]`); once it runs, follow "Automatic Integration Steps" to wire up a real project.

1. **Start a server**: in the project root of the handoff package run `python -m http.server 8000` (or `npx serve`);
   ES modules cannot be opened directly via `file://`.
2. **Open**: visit `exports/generic/demo/index.html` in a browser.
3. **Verification**: the browser Console shows `[kui-demo] event=boot screens=7` (when the atlas is missing,
   `atlas=missing` and a placeholder panel is used); the bottom nav switches 7 screens, and each tap/switch logs one
   `[kui-demo]` line (format in `demo/README.md`).
4. **Port**: once the demo proves the data is self-consistent, port the `uvRect` / `drawNineSlice` / two-state image-swap logic to the target engine per the "Mapping Reference".
5.
1. **Next**: use `ui-main.json` as the single source of truth for the real project, and mirror the demo's assembly approach against the "Mapping Reference" below.

(`ui-main.json`)

| Field | Meaning |
|---|---|
| `schema_version` | Manifest version, currently `1` |
| `engine` | `generic` |
| `atlas_id` / `atlas_size` | Atlas ID and pixel size `[w, h]` |
| `texture` | Atlas image path |
| `sprites` | **Full passthrough** of the Atlas packing result (same shape as `assets/atlases/*.json`) |

Common fields of a single sprite:

| Field | Meaning |
|---|---|
| `region` | `[x, y, w, h]` atlas rectangle |
| `pivot` | `[px, py]` 0–1 pivot |
| `slice.type` | `9-slice` \| `full` \| `1:1` \| `tile` |
| `slice.margins` | `[left, right, top, bottom]` (9-slice only) |
| `component_id` / `state` | Semantic component and state |
| `text_policy` | Text policy (e.g. `no-text`) |

## Two-State (normal / pressed)

Clickable controls must provide both `default` and `pressed` states (same `component_id`, different `state` entries):
Bind them as the control's normal / pressed skins on the engine side. For clickable controls missing a pressed entry in the atlas, go back to the component breakdown stage
to fill it in before export; when the demo lacks it, fall back to a darkened normal state (≈14%) so the two states remain distinguishable.

## Automatic Integration Steps (Agent)

1. **Parse the manifest**  
   Read `ui-main.json` and use `sprites` as the single source of truth; do not guess regions.

2. **Load the atlas**  
   Load the bitmap at the `texture` path; if the target engine does not support SVG, use the rasterized PNG (`assets/atlases/*.png`).

3. **Build a texture/sprite descriptor for each sprite**  
   - `region` → UV or pixel crop  
   - `pivot` → anchor/pivot  
   - `slice.type = 9-slice` + `slice.margins` → stretchable 9-slice  
   - `tile` → repeatable tiling  
   - `1:1` / `full` → natural size or scaled to the container (keep ratio)

4. **Compose UI by component and screen**  
   - Use `component_id` + `state` for control skins (button default/pressed/disabled).  
   - Screen structure: see `../../exports/taptap-maker/screens.json` or `contracts/screen-contract.yaml`.  
   - `text_policy = no-text`: image only, overlay text with the engine's Label.  
   - Colors / corner radius / font sizes: use `../../exports/web/tokens.css` or `contracts/style-contract.yaml`.

5. **Self-check**  
   - 9-slice keeps corners undistorted after stretching.  
   - Every `region` is inside the atlas bounds.  
   - Semantic names are unique and state-switch mappings are correct.

## Reference Demo (demo/)

`demo/` is a **runnable reference implementation** shipped with the exporter: the fixed-template assembler reads `ui-data.js`
(an engine-language mirror of `ui-main.json`) and assembles each screen into a node tree by layout regions,
with every event and screen switch printing one `[kui-demo]` line. Use cases:

- **Smoke test**: run it once to check whether the handoff JSON is self-consistent (region/margins/screen structure);
- **Reference implementation**: when integrating a real project, mirror the demo's assembly approach to reduce guesswork.

See `demo/README.md` for details and verification steps.

## Boundaries

- Does not generate any native engine project or importer output.
- Does not assume the target framework's node tree / component system; the Agent adapts per the table above.
- Business logic, input, and networking are wired up by the game project itself.

## Regenerate

```bash
kui export specs/laohuang-battle --force
```

Prerequisite: `contracts/atlas-contract.yaml` is packed/approved and `export-contract.yaml` contains `engine: generic`.
